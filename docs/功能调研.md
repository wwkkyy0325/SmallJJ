# SmallJJ 健康 · 核心功能实现路径调研

调研对象：本仓库（Flutter 3.44.4 / Dart 3.12.2，本机实测版本）+ 6 个核心功能点的落地技术路径。
约束：**全部数据与计算留在端侧**，不为体验牺牲核心；功能不堆冗余。

---

## 0. 结论摘要

| # | 功能 | 采用的路径 | 关键依赖 | 主要风险 |
|---|------|-----------|---------|---------|
| 1 | 体重记录（早/晚/任意时刻） | SQLite 单表 + 时段槽（morning/evening/any）+ 覆盖式 upsert + EWMA 趋势 | drift + sqlite3 | 基本无 |
| 2 | 接小布意图框架 | 双轨：①**立刻可做**的 Shortcut/Deep-Link/小组件（纯端侧）②按 T/TAF 283-2025 实现**意图注册+意图调用**（小布调 App，端侧 ContentProvider） | OPPO 开发者资质、意图名/serviceId 由 OPPO 下发 | 资质与垂域是否开放不可控；**意图共享**方案需上云，与"全本地"冲突 |
| 3 | 经期管理 | 本地事件表 + 最近 6 周期中位数预测 + 区间与置信度（不给单一日期当真理）+ 与体重/热量的联动标注 | 纯 Dart 算法 | 医疗合规；不规则周期预测必然不准 |
| 4 | 饮食热量规划 | 预算制（TDEE − 计划缺口）+ 四餐格 + 本地食物库（自建 600–1200 条）+ 常用/复制昨日 | 食物成分数据许可 | 食物库版权与维护成本 |
| 5 | 每日热量消耗 | 三档：公式法（Mifflin-St Jeor × PAL）→ 步数/运动叠加 → **14 天后自适应校准**（能量平衡反解） | Health Connect / 计步传感器 | 估算误差必然存在，必须UI标注"估算" |
| 6 | 热量缺口 | 定义唯一口径：`TDEE − 摄入`（运动不再二次叠加），并做安全钳制（≤25% TDEE、最低摄入、BMI<18.5 关闭减脂） | 5 的结果 | 口径混乱会让三个页面互相打脸 |
| 7 | 食物热量猜算 | 四级降级：本地搜索 → 中文数量词解析 → 拍照分类（TFLite，自训品类）→ 端侧 LLM 归一到食物库 ID | 端侧模型 | 拍照估热量误差大，只能给区间 |
| 8 | AI 健康分析 | **规则引擎产出事实，端侧 LLM 只做措辞**（禁止模型算数/新增数字），否则回退模板 | flutter_gemma + Gemma 3 1B/Qwen3 0.6B | 机型 RAM/发热；模型包体积 |

技术栈定版：
`drift`（SQLite）+ `sqlite3_flutter_libs`（+ 可选 `sqlcipher_flutter_libs` 加密）、`flutter_local_notifications`、`health`（Health Connect）、`flutter_gemma`（端侧 LLM，LiteRT-LM 后端）、原生 Kotlin 插件承载意图框架与 TFLite。
**不引入**：云同步、账号体系、推送、心率/血氧、饮水、社交——与核心无关。

## 1. 现状

- 现有代码是**纯 UI 演示**：`lib/data/health_snapshot.dart` 里 `DemoHealthData.snapshot()` 造数，`HealthRepository.load()` 假装延迟 320ms；没有持久化、没有真实业务。
- 底部 4 个入口：`首页 / 趋势 / 运动 / 我的`（`lib/ui/shell/app_nav.dart`），已有设计系统 `lib/theme/tokens.dart`、通用卡片 `lib/ui/common/*`，可直接复用。
- 演示指标里的静息心率、血氧、饮水与核心功能无关，属于要砍掉的部分（见 §6）。

结论：**不是"接入后端"，而是"从 0 建数据层 + 6 个领域模块"**，UI 骨架可留。

## 2. 总体架构（全本地）

```
UI (existing widgets)
  └ 页面/交互  lib/ui/...
Domain（纯 Dart，可单测，无 Flutter 依赖）
  ├ weight/    记录、趋势、时段判定
  ├ energy/    BMR / TDEE / 缺口 / 安全钳制
  ├ food/      搜索、数量词解析、份量换算
  ├ cycle/     周期预测、阶段、症状
  └ insight/   规则引擎（事实）→ LLM 文案层
Data
  ├ drift 数据库（唯一真相源）+ 迁移 + 导出/导入 JSON
  ├ 平台通道：Health Connect、通知、意图框架、TFLite、LLM
  └ 只读种子：食物库 SQLite asset（首次启动导入或直接 attach）
```

三条硬规则：

1. **数字只在一个地方算**：UI 不自己算缺口/趋势，全部走 Domain。
2. **一切写入带来源**（manual / intent / health_connect / import）与幂等键，方便去重与回溯。
3. **默认无网络**：正式包不声明 `INTERNET` 权限；模型下载与食物库更新做成独立构建变体或用户显式动作（见 §5.6）。

## 3. 功能点实现路径

### 3.1 体重记录（核心，最高频）

**用户真实动作**：早上起床上完厕所 → 站上秤 → 打开 App → 输一个数。要求 ≤3 次点击、0 次键盘弹出（可选）。

实现路径：

1. **入口三处**：首页体重大卡（点击=今日最近一条的编辑，长按=新增）、记录页顶部、通知/桌面小组件/小布（§3.2）。
2. **输入体验**：默认聚焦上次值，滚轮 + `−0.1 / +0.1` 大按钮，键盘只在用户主动点数字时出现；确认后立即出"较 7 天前 −0.3 kg"的即时反馈（用趋势值比较，不用昨日原始值）。
3. **时段槽自动判定**（用户可改）：`05:00–11:00 → morning`、`18:00–24:00 → evening`、其余 `any`。界面语言用"早上/晚上/刚才"，不出现"morning slot"。
4. **存储模型**：`weight_entry` 表（DDL 见《数据模型与算法.md》）。`(local_date, slot)` 对 morning/evening 唯一 → 同一天同一时段重复记录是**覆盖**（弹一次轻确认"更新为 65.2 kg?"），`any` 允许多条。
5. **趋势算法**：EWMA（α=0.15，缺测按天数衰减），同时算 7 日均值、周均差值、30 天斜率。图上线只画趋势线 + 原始点淡显。理由：日体重波动 ±1 kg 属正常（糖原/钠/水/排便），直接用原始点解读会让用户误判失败，这是体重类产品第一大流失点。
6. **与 Health Connect 双向**：写入 `WeightRecord`；读取时按 `external_id` 去重，来源标 `health_connect`，不覆盖手输数据。
7. **校验与容错**：20–300 kg、一位小数；与上次值差 >3 kg 时二次确认（多半是打错/换秤）；支持删除与改时间。
8. **提醒**：早 07:00 / 晚 21:30 本地通知，可单独关；通知带上"昨天 64.8 → 今天?"文案提升转化。

验收：冷启动到记录完成 ≤5s；断网可用；同日早晚各一条不互相覆盖；趋势线与原始点在同图不误导。

### 3.2 接入小布意图框架（最需要先定方案的一块）

先说结论：**"小布能调我的 App"有标准路径，但要走 OPPO 的意图生态准入；"我的 App 把数据推给小布出卡"那套必须上云，和"全本地"直接冲突。** 所以要分两条轨并行，先上不依赖资质的兜底轨，保证用户体验不空转。

#### 路径 A（兜底，1–2 天可上线，纯端侧）

| 手段 | 能力 | 说明 |
|------|------|------|
| Android 动态/静态快捷方式（`ShortcutManager` + `shortcuts.xml`） | 长按图标 / 小布指令里选"应用快捷方式"→ 直达"记体重" | 零资质，官方支持 |
| Deep link：`smalljj://record/weight?kg=65.2&slot=morning&id=<uuid>` | 任意来源（小布、快捷指令、二维码、通知）跳转到预填页面 | App Links 用 `intent-filter` 处理，`id` 做幂等 |
| 桌面小组件（AppWidget / Glance） | 显示今日体重与缺口，一键进记录 | 端侧，体验收益高 |
| 小布指令（Breeno/小布指令，本地自动化） | 用户自建"每天 7:00 打开记录体重" | 用户侧配置，App 只需暴露入口 |

这一层不承诺"语音说一句就记下"，但**先把路径打通**，等准入下来再换成真正的语音意图，UI 不用改。

#### 路径 B（正式接入，需 OPPO 准入）

OPPO 官方文档把接入方式描述为"基于**意图共享**接入 OPPO 意图框架"，落点是**流体云**、**小布建议卡片**，接入步骤含"账号关联（云侧）""获取 client_id / client_secret / accessToken"——也就是**意图数据经 OPPO 云**，卡片由 OPPO 侧渲染。对健康数据这类敏感信息，这条路只能传粗粒度/脱敏信息（例如"今天还没记体重"这种提醒），**不能传具体体重、经期、摄入**。

真正的"小布 → App 执行动作"在行业标准里叫**意图调用**。电信终端产业协会标准 **T/TAF 283-2025《智能终端意图框架接口技术要求》**（起草单位含信通院、OPPO、vivo、荣耀、小米、华为、蚂蚁）把端侧方案写得很具体，可直接按它实现，**一次实现多厂商可用**：

- 通信层：`ContentProvider`，同步走 `call()`，异步走 `ResultReceiver`。
- 能力三件套：**意图注册**（`AndroidManifest.xml` 配置 + 意图注册文件，意图命名规则固定）、**意图共享**（App → 系统）、**意图调用**（系统 → App，分**前台模式**与**后台模式**，参数为 `IntentParams`）。
- 鉴权用系统权限，标准中出现的权限名为 `intelligent.permission.SHARE_INTENT`（共享）与 `intelligent.permission.EXECUTE_INTENT`（被调用）——**具体拼写与 protectionLevel 以标准原文/OPPO 文档为准，不要凭猜写进 Manifest**。

落地骨架（Kotlin 侧，Dart 用 MethodChannel 调）：

```kotlin
// 被小布调用：意图执行入口。method 名与 IntentParams 结构需按标准 5.5 节核对
class IntentCallProvider : ContentProvider() {
    override fun call(method: String, arg: String?, extras: Bundle?): Bundle? =
        when (method) {
            "executeIntent" -> handleExecute(arg, extras)   // 后台模式：无 UI 直接落库
            else -> null
        }
    // ... onCreate/query/insert/delete 按标准要求返回 null 或空 Cursor
}
```

```xml
<provider
    android:name=".intent.IntentCallProvider"
    android:authorities="${applicationId}.intent"
    android:exported="true"
    android:permission="intelligent.permission.EXECUTE_INTENT" />
```

建议注册的意图清单（名称必须用 OPPO 垂域清单里的官方名，**下面只是我方能力清单**）：

| 能力 | 参数 | 缺槽位时 | 幂等 |
|------|------|---------|------|
| 记录体重 | `weight_kg`（必填）、`slot`、`time` | 回问"多少公斤？"或拉起输入页 | 用 `IntentParams` 的 identifier |
| 查询体重摘要 | `range`（7d/30d） | 默认 7d | 只读 |
| 记录一餐 | `food_text` 或 `food_id + grams` | 拉起搜索页 | 同上 |
| 查今日预算 | — | — | 只读 |
| 记录经期开始 | `date` | 默认今天 | 同日唯一 |

**必须先确认的外部前提（不能自己假设）**：
1. 个人/企业开发者能否申请意图框架接入，健康垂域是否开放，是否要求资质（医疗类内容常被额外审核）。
2. 意图名、`serviceId`、正式环境的联调方式由 OPPO 下发，开发期只有 `Example.*` 调测模板。
3. 若仅支持"意图共享"而不给"意图调用"，则"语音记账"这条需求在纯端侧无解，只能留在路径 A + 自有语音输入。

#### 路径 C（未来兼容，别现在做）

Android 16 起有平台级 **AppFunctions**（MCP 风格，`@AppFunctionDeclaration`，调用方需 `EXECUTE_APP_FUNCTIONS`，面向 Gemini 等助手，2026 年 5 月仍为受邀私测）。它是"App 把能力暴露成工具"的标准方向，实现成本主要在 Kotlin 声明层。**ColorOS 是否支持 AppFunctions 目前无法证实**，因此列为观察项：在路径 B 的 Provider 里把业务逻辑抽成 `IntentHandlers`，将来换壳即可。

**推荐执行顺序**：路径 A 立刻做 → 同步提交 OPPO 准入 → 准入下来按 B 实现（复用 A 的 handler 与幂等键）→ 关注 C。

### 3.3 经期管理

定位：**记录 + 预测 + 与体重/热量的联动解释**，不做医疗诊断，不做避孕宣称。

实现路径：

1. **模型**：`cycle_event`（经期开始/结束，`start_date` 唯一）+ `cycle_day_log`（流量 0–3、疼痛、情绪、症状、基础体温、用药）。删掉"开始/结束"配对歧义：只记开始，结束可后补；进行中的周期允许开放。
2. **预测算法**（纯 Dart，可单测）：
   - 周期长度 = 最近 ≤6 次 start-to-start 间隔，剔除 <15 或 >60 天的异常值后取**中位数**；
   - 下次开始 = 最近一次开始 + 中位周期；**同时输出区间** `中位周期 ± 标准差`；
   - 排卵日 ≈ 下次开始 − 14 天（黄体期个体 11–16 天，所以给 5 天窗）；
   - 置信度：SD ≤2 天=高、3–4=中、>4=低（低置信度只显示区间，不显示具体日期）。
3. **不规则提示**：最近 6 个周期中 ≥2 个落在 21–35 天之外 → 提示"建议咨询医生"，不做诊断。
4. **与体重联动（这是差异化体验，但必须诚实）**：体重图上叠加经期色带；经前 3 天到经期第 2 天出现 +0.5–2 kg 时，主动解释"多为水潴留，趋势线已平滑"。**不要**把"黄体期代谢 +5%"当公式写死——2026 年的系统综述结论是各研究不一致（有的研究 24h 能量消耗在黄体期升 8–16%，有的测不出 RMR 差异）。因此默认不减不加，只在经期前后把缺口上限放宽一档并在文案里说明。
5. **合规**：首次使用弹一次说明（预测非避孕手段、非诊断）；敏感字段只在本地库，导出默认不含。
6. **入口**：趋势页（周期长度图 + 体重叠加）、首页一张"今天 周期第 12 天 · 预计 5 天后"的小卡、记录页一键"今天来了"。

验收：少于 2 个周期时只显示"记录中"不预测；跨年、跨时区、补录历史周期不崩；删除一个周期后预测立即重算。

### 3.4 饮食热量规划

以"预算"为核心，不做食谱商城、不做社交打卡。

实现路径：

1. **目标 → 预算**：`目标体重 + 速率(0.25/0.5/0.75 kg/周)` → 计划缺口 `= 速率 × 7700 / 7`（0.5 kg/周 ≈ 550 kcal/天；7700 kcal/kg 是脂肪能量密度的工程常用值，非精确生理常数）→ `kcal_target = TDEE − 缺口`，再经安全钳制（§3.6）。
2. **宏量分配**：蛋白 `1.6–2.2 g/kg`（减脂保肌）、脂肪 `0.6–1.0 g/kg`、碳水补足；按四餐格（早/午/晚/加餐）给比例预算，用户可改。展示"还剩 420 kcal，蛋白还差 35 g"，比只显示卡路里更有用。
3. **每餐交互**：搜索（中文名 + 拼音全拼 + 首字母 + 别名）→ 选份量（一碗/一个/一份，或直接克数）→ 落库。**最近吃过的**与**常吃**置顶；"复制昨天早餐"一次点击；长按可改份量、删条目。
4. **超出预算的体验**：不报警、不红屏。给"今天还差 120 kcal 蛋白，建议加一杯无糖酸奶（≈90 kcal）"这类可执行建议，缺口为负时用同一套语言。
5. **食物库（必须自建，不能直接抄）**：

| 来源 | 许可 | 用法 |
|------|------|------|
| USDA FoodData Central | 美国政府作品/公有领域（站点明确 "in the public domain"） | 营养素基线、西式/通用食材 |
| 中国食物成分表（第 6 版，北大医学出版社） | **有版权**；GitHub 上 OCR 版明确标注仅限非商业 | 只能作**内部校对参考**，不能打包分发；商用需向中国疾控中心营养与健康所授权 |
| Open Food Facts | ODbL（署名 + 同类共享） | 包装食品条码（可选，非核心） |

   因此路线是：**自建 600–1200 条"中式家常 + 常见外食"条目**，每条含名称/别名/拼音/每 100 g 能量与三大营养素/可食部/常见份量（一碗 150 g、一个鸡蛋 50 g 之类的**实测或标注来源**的克数），标注 `source` 与 `verified`，开放用户纠错。宁可条目少而准，也不要 10 万条错的。
6. **数据质量策略**：条目上线前置三条检查（能量与三大营养素自洽：`4P+9F+4C` 与 kcal 偏差 ≤10%；份量克数在合理区间；别名可搜到）。用户改动后记 `user_edited`，用于后续修正种子。

### 3.5 每日热量消耗（TDEE）

三档递进，UI 上永远标"估算"，并显示用的是哪一档。

1. **公式法（第 1 天就能用）**：Mifflin-St Jeor
   `男：10W + 6.25H − 5A + 5`，`女：10W + 6.25H − 5A − 161`（W=kg，H=cm，A=岁）；
   `BMR × PAL`，PAL 取 1.2 / 1.375 / 1.55 / 1.725（久坐/轻度/中度/高度）。
   W 用**趋势体重**而非今天的原始值。
2. **活动叠加（当天更贴近）**：`BMR × 1.2 + 步数消耗 + 运动消耗`
   - 运动：`kcal = MET × 3.5 × kg / 200 × 分钟`（MET 表内置：快走 4.3、慢跑 8.3、骑行 8.0…）；
   - 步数：`kcal ≈ 步数 × 0.00045 × kg`，属经验系数，必须由第 3 档校准。
3. **自适应校准（第 14 天起，最重要）**：能量平衡反解
   `维护 ≈ 平均摄入 − 7700 × 趋势体重斜率(kg/天)`，
   斜率用最近 14–28 天的 EWMA 体重做线性回归；要求 ≥10 天有体重、饮食记录覆盖率 ≥80%。
   然后 `TDEE = 0.7 × 自适应 + 0.3 × 公式`，每周调整上限 ±150 kcal/天（避免剧烈跳变）。
   数据不足时停在 1/2 档，并明确告诉用户"再记 6 天就能更准"——这是提升长期留存最有效的钩子。

**数据来源**：Health Connect 读步数/运动/睡眠（Android 14+ 系统内置，13 及以下需装 HC 应用）；无授权时降级为"手动活动水平"，功能不残废。

### 3.6 热量缺口

**只允许一个定义**：`缺口 = TDEE(当天) − 摄入(当天)`。运动消耗已包含在 TDEE 里，**不得再减一次**，否则三个页面数字互相矛盾。

- 展示三层：今日缺口、本周累计缺口、按 7700 kcal/kg 折算的"预计本周体重变化"（写"约"，给区间）。
- **安全钳制**（不满足就不许设这个目标，而不是事后警告）：
  - 缺口 ≤ 25% TDEE；
  - 摄入不低于常见临床下限（女约 1200、男约 1500 kcal/天）——这组数值在多份减重指南与实践里被引用，但**上线前必须核对权威指南原文的适用条件**，不要当医学结论硬编码进文案；
  - 每周降重 ≤1% 体重；
  - BMI < 18.5 或孕期/哺乳标注时**关闭减脂模式**，只保留维持与记录。
- 缺口为负（吃超了）时不做道德评判，只给"明天怎么调"。

### 3.7 食物热量大致猜算

四级降级，**任何一级的结果都必须落回食物库条目 + 克数**才允许入库，这样才可解释、可修正。

1. **Tier 0 本地搜索**：覆盖 80% 场景，命中即用。
2. **Tier 1 文本解析**（纯 Dart，最有性价比）：中文数量词 + 单位的正则切分，再对词表做最长匹配。
   例："两个鸡蛋 一杯牛奶 半碗米饭" → `[(鸡蛋,100g),(牛奶,250g),(米饭,75g)]`。
   规则要点：数字含中文（一/两/半/几）、容量单位（杯/碗/勺）按 `serving_json` 换算、未命中词保留 `free_text` 并标记低置信度、**始终让用户确认一次**。
3. **Tier 2 拍照**：端侧图像分类（TFLite MobileNetV3 / MediaPipe Image Classifier，300–500 类中式菜品，**自采数据微调**）。输出 top-3 菜名 + 默认份量，用户选一个再调份量。
   为什么不做"像素级体积/热量估计"：那需要深度相机与专用数据集（Nutrition5k 一类），精度与工程成本都不匹配本产品。公开数据集（如 Food-101）的图片许可也只允许科研范围内使用，商用需重新谈——**不要拿它直接训商用模型**。
4. **Tier 3 端侧 LLM 归一化**：只在 Tier 1 失败时用，任务限定为"把用户的话映射到给定候选食物 + 估计克数"，输出 JSON。模型绝不直接给 kcal。
5. **误差表达**：单餐估误差现实区间是 ±20–30%，所以 UI 显示"约 520 kcal（480–560）"，不显示 523 kcal 这种假精度；拍照来源加小标"猜的，可改"。

---

### 3.8 端侧 AI 健康分析

**架构原则：模型不算数，只说话。**

1. **规则引擎（必做，是产品主体）**：20–40 条可解释洞察，输入是聚合后的统计（趋势、均值、覆盖率、周期阶段），输出结构化 `Insight{code, severity, evidence(numbers), action}`。示例：
   - `weight_trend_flat`：连续 14 天趋势斜率 ≈0 且缺口 >300 → "热量缺口有了但体重没动，先看记录覆盖率（当前 62%）"；
   - `protein_low`：近 7 天蛋白均值 0.9 g/kg → 给具体补法；
   - `cycle_water_retention`：经前 +0.8 kg → 解释而非报警；
   - `logging_gap`：连续 3 天没记 → 降低门槛（"只记体重也行"）。
   纯 Dart、0 延迟、可单测、可复现——这也保证了没有模型/低端机时体验不降级。
2. **LLM 文案层（可选开关）**：把上面的事实 JSON 交给端侧模型改写成人话（≤120 字、只陈述、不给诊断）。
   - 运行时：`flutter_gemma`（LiteRT-LM C API 后端），模型选 `Gemma 3 1B`（约 0.5 GB）或 `Qwen3 0.6B`（更小，中文够用）；
   - **护栏**：抽取输出里的所有数字，必须落在输入事实集合 ±5% 内，否则整段回退到模板文案；提示词里禁掉"诊断/用药/疾病"类输出；
   - 触发时机：用户主动点"生成分析"或每周一次，**不在启动路径上跑**，用流式输出 + 可取消；
   - 设备门槛：RAM ≥6 GB 且 ABI 支持才展示入口，否则隐藏（体验优先于"功能存在"）。
3. **周报**：模板 + 本地图表 + 导出图片/PDF（本地生成，不联网）。
4. **语音输入**（可选）：优先用系统/小布侧 ASR（`SpeechRecognizer.createOnDeviceSpeechRecognizer`，API 31+）；注意**国产 ROM 的端侧识别服务不保证存在**（本项目目标机是 ColorOS，需实测），兜底是内置 sherpa-onnx 中文离线模型（体积与许可需实测确认）或干脆只留键盘输入。

## 4. 横切事项

- **存储**：`drift` + schema 迁移（`schemaVersion` 逐版迁移，每条迁移有测试）；加密用 SQLCipher + Android Keystore 存密钥（`flutter_secure_storage`）；导出/导入 JSON（可选加密 zip），这是"全本地"产品的必备逃生门。
- **隐私**：正式包去掉 `INTERNET` 权限；模型/词库更新用单独变体；设置页放一个"本 App 不联网、数据只在本机"的说明页，比任何隐私政策都好用。
- **通知**：`flutter_local_notifications`；Android 13+ 运行时通知权限、精确闹钟需单独申请——提醒是体重记录的主要入口之一，必须实测各机型。
- **性能**：首页冷启动 ≤1.5 s；体重保存到图表刷新 ≤100 ms；30 天曲线用 `CustomPainter` + 预聚合，不逐点建 Widget。
- **无障碍/易用**：数值输入支持大字号与单手操作；所有图标按钮 ≥48×48；颜色不做唯一语义载体（缺口正负同时有文字）。
- **合规文案**：非医疗器械、不提供诊断、经期预测不可用于避孕；把这些写进首次引导而不是藏在设置里。

## 8. 待核实清单（不要凭印象写进代码）

1. OPPO 是否对个人开发者开放意图框架接入；"意图调用"是否属于可申请能力；健康垂域是否存在官方意图名。
