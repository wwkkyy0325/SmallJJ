# 数据模型与算法规范

配套《功能调研.md》。目标：**建库一次到位，算法可单测，页面不自己算数**。

约定：
- 时间统一存 `INTEGER`（epoch ms, UTC），日期另存 `TEXT 'YYYY-MM-DD'`（设备本地时区），用于"按天"聚合。跨时区/改时区时以 `local_date` 为准。
- 所有表带 `created_at`；可编辑的带 `updated_at`。
- 数值一律 `REAL`，不做 int 分单位（体重/千卡都需要小数，且 SQLite 无 decimal）。

---

## 1. 表清单

| 表 | 用途 | 增长量级 |
|----|------|---------|
| `profile` | 单行配置：出生年/身高/活动水平/目标（无性别：固定女式 BMR） | 1 行 |
| `weight_entry` | 一次称重：时间 + kg（+ 体脂） | 1–3 行/天 |
| `food_item` | 食物库（种子 + 用户自建） | 600–1200 行（只读为主） |
| `food_fts` | 检索索引：名称/别名/拼音/首字母（FTS5，contentless） | 3–5 倍 food_item |
| `meal_entry` | 一餐（日期 + 餐次） | 3–5 行/天 |
| `meal_item` | 一餐里的条目（食物 + 克数 + 算出的热量） | 10–20 行/天 |
| `activity_log` | 运动记录 / 手动活动 | 0–3 行/天 |
| `daily_steps` | 步数缓存（Health Connect 聚合后的结果） | 1 行/天 |
| `day_target` | 每日预算快照（TDEE/缺口/宏量）**落库快照** | 1 行/天 |
| `cycle_event` | 经期开始/结束 | 12–14 行/年 |
| `cycle_day_log` | 经期每日症状/流量/BBT | 1 行/天 |
| `insight` | 生成的洞察 | 0–3 行/天 |
| `meta` | schema 版本、种子版本、偏好 | < 20 行 |

**为什么 `day_target` 要落库**：TDEE 会随算法升级/数据补录变化，历史页面必须还原"当时的预算"，否则昨天的"还剩多少 kcal"今天看会变。

## 3. 核心算法

### 3.1 体重口径：时间 + 数值

体重只存两件事：`measured_at`（什么时候称的）和 `weight_kg`（多少，两位小数）。
没有时段槽，也没有 `(local_date, slot)` 唯一约束。

- 链接没带时间 → 用当前时间；带 `time=08:00` / `date=2026-01-14` → 按给定值。
  旧的 `slot=morning|evening` 仍然认，翻译成 8:00 / 20:00，装了旧快捷方式也能用。
- 同一天记两次（早上一次、晚上一次）是两条记录：原始点两条都画，`dailyWeights()`
  取当天均值喂趋势。
- 改已有记录必须带 `id`：时间和数值一起改；不带 `id` 就是新增一条。

### 3.2 体重趋势（EWMA）

```dart
/// entries 按时间升序。alpha 越小越平滑。
List<TrendPoint> weightTrend(List<WeightEntry> entries, {double alpha = 0.15}) {
  final out = <TrendPoint>[];
  double? trend;
  DateTime? prev;   // 本地日期（当天 00:00）
  for (final e in entries) {
    if (trend == null) {
      trend = e.weightKg;
    } else {
      final gap = prev == null ? 1 : e.date.difference(prev).inDays.clamp(1, 30);
      final a = 1 - math.pow(1 - alpha, gap);   // 缺测越久，权重越大
      trend = trend + a * (e.weightKg - trend);
    }
    prev = e.date;
    out.add(TrendPoint(date: e.date, raw: e.weightKg, trend: trend!));
  }
  return out;
}
```

派生指标（同一函数内算，避免 UI 各算各的）：
- `delta7`：今天趋势值 − 7 天前趋势值（当天无记录时取最近一条的趋势值并标注"数据截至 X"）；
- `slope30`：最近 30 天趋势值的最小二乘斜率（kg/天），不足 10 个点返回 `null`；
- `weeklyAvg`：按自然周（周一为首日）算趋势值均值。

### 3.3 BMR / PAL

```
// 本应用只服务女性，所以只有女式；男式（+5）不做，也不用问性别。
BMR = 10*W + 6.25*H - 5*A - 161
A = 当前年份 - birth_year
W = 趋势体重（无趋势值时用最近一条原始值）
PAL: sedentary 1.2 / light 1.375 / moderate 1.55 / active 1.725
```

### 3.4 TDEE 三档

```dart
// 档 1：公式法（第 1 天可用）
double tdeeFormula(double bmr, ActivityLevel lvl) => bmr * palOf(lvl);

// 档 2：活动叠加（当天）
double tdeeActivity(double bmr, {required int steps, required double weightKg,
                                 required double workoutKcal}) {
  final stepKcal = steps * 0.00045 * weightKg;   // 经验系数，需被档 3 校准
  return bmr * 1.2 + stepKcal + workoutKcal;
}

// 运动：MET 公式
double workoutKcal(double met, double weightKg, double minutes) =>
    met * 3.5 * weightKg / 200 * minutes;

// 档 3：自适应（能量平衡反解）：吃进去的 − 体重变化折算的 = 消耗
// 条件：跨度 >=10 天、体重 >=5 天、摄入记录 >=70% 的天数
double? tdeeAdaptive({required double avgIntakeKcal,
                      required double trendSlopeKgPerDay,
                      required int days, required int weightDays}) {
  if (days < 10 || weightDays < 5) return null;
  return avgIntakeKcal - 7700 * trendSlopeKgPerDay;   // 7700 kcal ≈ 1 kg 脂肪
}
```

融合与防跳变：

```dart
double blendTdee({required double? adaptive, required double formula, required double? prev}) {
  if (adaptive == null) return formula;
  var t = 0.7 * adaptive + 0.3 * formula;
  if (prev != null) t = t.clamp(prev - 150, prev + 150);   // 每周最多 ±150 kcal/天
  return t;
}
```

`day_target.algo_version` 记录当前用的是哪档：`v1` = 纯公式，`v1+adaptive` = 经体重
记录校正。这个是给数据库和排查用的，界面上不显示。

### 3.4.1 斜率用最小二乘，不用首尾两点

```dart
/** 单位 kg/天，掉秤为负。 */
double? weightSlopeKgPerDay(List<DailyWeight> days);
```

两周里只要有一端那天多喝了 500 ml 水，`最后一条 − 第一条` 就整体歪掉，反解出的
TDEE 能差出三四百千卡；回归用上窗口里的每一天，单日水分被摊平。这是「拟合真实
消耗」里真正影响结果的一步，其余（7:3 混合、±150 kcal 钳制）只是防跳变。

### 3.5 估算消耗与收支（没有预算、没有目标）

```dart
class EnergyPlan {
  final double bmr, tdee;              // 估算消耗
  final double proteinG, fatG, carbG;  // 三餐参考克数，不设目标线
  final double adaptiveWeight;         // 0 = 全用公式，1 = 自适应生效
}

EnergyPlan planEnergy({
  required Profile profile,
  required double weightKg,
  required int year,
  double? adaptiveTdee,
}) {
  final age = ageFromBirthYear(profile.birthYear, year: year);
  final bmr = bmrFemale(
      weightKg: weightKg, heightCm: profile.heightCm, ageYears: age);
  final tdee = adaptiveTdee ?? bmr * palFor(profile.activityLevel);

  var proteinG = weightKg * 1.2;                       // 1.2 g/kg
  if (proteinG * 4 > tdee * 0.35) proteinG = tdee * 0.35 / 4;
  final fatG = (weightKg * 0.8).clamp(30.0, tdee * 0.35 / 9);
  var carbG = (tdee - proteinG * 4 - fatG * 9) / 4;
  if (carbG < 0) carbG = 0;

  return EnergyPlan(
    bmr: bmr, tdee: tdee, proteinG: proteinG, carbG: carbG, fatG: fatG,
    adaptiveWeight: adaptiveTdee == null ? 0 : 1,
  );
}
```

**删掉的部分**（曾经有，现在没有）：减脂/增重模式、目标体重、每周速率、计划缺口、
摄入预算、25% TDEE 封顶、每周 1% 体重封顶、BMI<18.5 关缺口。这些是「计划」——先定一个
速率，再反推今天该吃多少，然后用它评判今天。这个应用只做测量与统计，不做计划。

为什么删（实测教训）：封顶规则会静默改写用户看到的数。0.5 kg/周 对应 550 kcal，
被 25% 一路压到 488 kcal，摄入从 1403 变成 1465。规则本身不算错，但它造成的差别用户
既看不懂也改不了，最后的处理只能是「不显示」——而藏起来的规则不如没有。

**唯一口径**：`收支 = day_target.tdee − 当日摄入`。运动消耗已在 TDEE 内，禁止二次相减。
这个数只描述方向，不判定好坏：

```dart
String gapText(DayBalance b, double intake) => intake < 1
    ? '今天还没记饮食'                 // 没记就不报差值，早上那是噪音
    : b.magnitudeKcal < 1
        ? '和估算消耗持平'
        : b.isSurplus
            ? '比估算消耗多 ${kcalLabel(b.magnitudeKcal)} kcal'
            : '比估算消耗少 ${kcalLabel(b.magnitudeKcal)} kcal';
```

- 进度条整条 = 当日估算消耗，填充 = 已摄入，**没有预算刻度**。
- 不翻红、不翻绿，不写「超出」「缺口」「还剩多少」：多吃了不是错误，是今天的一个数据点。
- `intakeFloorFemale = 1200` 仍在，但只用来发一条「今天吃得太少」的提醒，不是上限，
  也不参与任何「还能吃多少」的计算。
- 落地：`day_target` 只存 `bmr / tdee / 三餐克数 / algo_version`；老表里的
  `intake_budget / deficit_kcal / note` 三列保留（省一次迁移），新写入给中性值，
  不再读、不再显示。

### 3.8 经期预测

```dart
class CyclePrediction {
  final DateTime? nextStart;        // 低置信度时为 null，只给区间
  final DateTime? windowStart, windowEnd;
  final DateTime? ovulation, fertileStart, fertileEnd;
  final int? medianCycle, sdDays;
  final Confidence confidence;      // high / medium / low
  final List<String> flags;         // {'irregular','too_short','too_long'}
}

CyclePrediction predict(List<DateTime> startDates, {int lookback = 6}) {
  final dates = [...startDates]..sort();
  if (dates.length < 2) return CyclePrediction.none();

  final intervals = <int>[];
  for (var i = 1; i < dates.length; i++) {
    final d = dates[i].difference(dates[i - 1]).inDays;
    if (d >= 15 && d <= 60) intervals.add(d);   // 剔除异常/补录造成的脏间隔
  }
  final recent = intervals.reversed.take(lookback).toList();
  if (recent.isEmpty) return CyclePrediction.none();

  final median = _median(recent);
  final sd = _stdDev(recent);
  final last = dates.last;
  final next = last.add(Duration(days: median));

  final conf = sd <= 2 ? Confidence.high : sd <= 4 ? Confidence.medium : Confidence.low;
  final ovulation = next.subtract(const Duration(days: 14));

  return CyclePrediction(
    nextStart: conf == Confidence.low ? null : next,
    windowStart: last.add(Duration(days: median - math.max(2, sd.ceil()))),
    windowEnd:   last.add(Duration(days: median + math.max(2, sd.ceil()))),
    ovulation: ovulation,
    fertileStart: ovulation.subtract(const Duration(days: 5)),
    fertileEnd:  ovulation.add(const Duration(days: 1)),
    medianCycle: median, sdDays: sd, confidence: conf,
    flags: [
      if (recent.length >= 2 && recent.any((d) => d < 21 || d > 35)) 'irregular',
      if (median < 21) 'too_short',
      if (median > 35) 'too_long',
    ],
  );
}
```

阶段判定（用于文案与热量联动）：`经期 = start..start+中位经期长度-1`；`黄体期 = 排卵后`；其余为卵泡期。
**默认不因阶段调整 TDEE 数值**，也不调整任何预算（应用没有预算），仅在经期前后给出"体重可能 +0.5–2 kg 水潴留"的解释。

### 3.9 洞察规则引擎

规则是纯函数：`Insight? evaluate(Metrics m)`，`Metrics` 由查询层一次算好。

| code | 条件（示例阈值） | severity | 动作 |
|------|-----------------|----------|------|
| `no_weight_today` | 今日无体重且当地 ≥10:00 | action | 一键记录 |
| `weight_trend_flat` | 14 天斜率 ∈ [-0.02, 0.02] kg/天 且 记录覆盖率够 | warn | 看记录覆盖率 |
| `protein_low` | 7 天蛋白均值 < 1.2 g/kg | info | 加蛋白的具体建议 |
| `intake_too_low` | 当天摄入 < 1200 kcal 且已过 20:00 | info | 只陈述，白天不判 |
| `logging_gap` | 连续 ≥3 天无饮食记录 | info | 降低记录门槛 |
| `cycle_water` | 经前 3 天至经期第 2 天体重 +0.5~2 kg | info | 解释，不改任何数值 |
| `streak_7` | 连续 7 天有体重记录 | info | 正向反馈（不诱导过量记录） |

LLM 文案层护栏：

```dart
bool narrationIsSafe(String text, Set<String> allowedNumbers) {
  final nums = RegExp(r'\d+(?:\.\d+)?').allMatches(text)
      .map((m) => double.parse(m.group(0)!));
  for (final n in nums) {
    final ok = allowedNumbers.any((s) {
      final v = double.parse(s);
      return v == 0 ? n == 0 : (n - v).abs() / v <= 0.05;   // ±5%
    });
    if (!ok) return false;                                  // 出现新数字 → 回退模板
  }
  const banned = ['诊断', '治疗', '吃药', '停药', '疾病'];
  return !banned.any(text.contains);
}
```

## 4. 校验规则（写入前必查，集中在一处）

| 场景 | 规则 | 表现 |
|------|------|------|
| 体重 | 20–300 kg，保留 1 位小数 | 超范围禁用保存 |
| 体重跳变 | 与上一条差 >3 kg | 二次确认"是不是 63.5 打成 6.35？" |
| 同日同一分钟 | 已有一条 | 不覆盖，两条都留（要改就带 id） |
| 餐次克数 | 0 < g ≤ 5000 | 超范围不保存 |
| 食物条目 | `4P+9F+4C` 与 kcal 偏差 >10% | 种子导入时拒收（用户自建允许并标 `verified=0`） |
| 目标速率 | —（应用没有目标，此规则已删除） | — |
| 经期 | `start_date` 唯一；`end_date ≥ start_date` | 冲突提示"这天已记录" |
| 时间 | `measured_at` 不得晚于现在 +5 min | 禁用保存 |

## 6. 迁移与种子

- `schemaVersion` 1 起步，每次改表写 `MigrationStrategy.onUpgrade` 并附迁移测试（建 v1 库 → 升级 → 查询关键字段）。
- 日期列全部 `TEXT 'YYYY-MM-DD'`，禁止存 `DateTime` 字符串（跨版本格式不稳）。
- 食物库种子：`assets/seed/food_v1.json` + `meta.seed_version`；升级时按 `name+cooked_state` upsert，**不覆盖用户改过的行**（`is_custom=1` 或 `user_edited` 跳过）。
- 导出格式：`{schemaVersion, exportedAt, profile, weight, meals, activity, cycle, meta}`，导入按 `external_id`/自然键去重，冲突以导入方为准并提示。
